# Alarm Catalog

---

# Purpose

This document defines the alarm management philosophy, alarm numbering system, severity levels, acknowledgement rules and recovery procedures for the AquaFeed PLC software.

All alarms generated by the PLC software shall comply with this document.

---

# Objectives

The alarm system shall:

- Detect abnormal operating conditions
- Protect personnel and equipment
- Assist troubleshooting
- Reduce downtime
- Provide historical traceability
- Standardize alarm behavior across all modules

---

# Alarm Structure

Every alarm shall contain the following information.

| Field | Description |
|---------|-------------|
| Alarm ID | Unique alarm number |
| Alarm Name | Short descriptive title |
| Module | Source Function Block |
| Severity | Alarm priority |
| Category | Alarm classification |
| Description | Detailed explanation |
| Cause | Possible root cause |
| Recommended Action | Operator response |
| Reset Type | Automatic or Manual |

---

# Alarm Numbering

Alarm IDs shall be grouped by subsystem.

| Range | Module |
|---------|---------|
| 1000–1099 | System Manager |
| 1100–1199 | Communication |
| 1200–1299 | Selector |
| 1300–1399 | Blower |
| 1400–1499 | Dosing |
| 1500–1599 | Recipe Manager |
| 1600–1699 | Job Manager |
| 1700–1799 | Maintenance |
| 1800–1899 | Runtime |
| 1900–1999 | General System |

# Severity Levels

## Information

Characteristics

- Informational only
- No production impact
- No operator action required

Example

- Recipe Loaded

---

## Warning

Characteristics

- Production continues
- Operator attention recommended

Examples

- Maintenance Due Soon
- Communication Delay
- Runtime Limit Approaching

---

## Alarm

Characteristics

- Production may stop
- Operator intervention required

Examples

- Motor Overload
- Position Timeout
- Sensor Failure

---

## Critical

Characteristics

- Immediate shutdown
- Equipment protection
- Safety priority

Examples

- Emergency Stop
- Drive Fault
- PLC Communication Lost
- Safety Circuit Open

# Alarm Life Cycle

```text
Normal

↓

Fault Detected

↓

Alarm Active

↓

Operator Acknowledgement

↓

Fault Cleared

↓

Reset

↓

Normal
```

---

# Alarm Acknowledgement

Acknowledgement confirms that the operator has seen the alarm.

Acknowledgement shall **not** clear the alarm.

The alarm remains active until:

- Cause removed
- Reset conditions satisfied

---

# Alarm Reset Types

## Automatic Reset

Examples

- Temporary communication delay
- Sensor recovered
- Network restored

---

## Manual Reset

Examples

- Emergency Stop
- Drive Fault
- Mechanical Failure
- Safety Circuit Fault

Manual reset requires operator confirmation.

---

# Alarm Logging

Each alarm event shall record:

- Alarm ID
- Timestamp
- Module
- Severity
- Active Duration
- Operator
- Reset Time

The log shall remain available for diagnostics.

---

# Alarm Display

The HMI shall display:

- Alarm ID
- Alarm Name
- Severity
- Time
- Current Status
- Recommended Action

Critical alarms shall be visually distinguishable from warnings.

---

# Alarm Priority

Priority order:

1. Emergency Stop
2. Safety Fault
3. Electrical Fault
4. Communication Fault
5. Mechanical Fault
6. Process Fault
7. Information

Higher-priority alarms shall never be hidden by lower-priority alarms.

---

# Alarm Naming Rules

Alarm names shall:

- Be concise
- Clearly describe the fault
- Avoid abbreviations
- Use consistent terminology

Preferred examples:

- Blower Overload
- Selector Position Timeout
- Dosing Motor Fault
- Modbus Communication Lost

Avoid examples:

- Error 1
- Fault
- Alarm A
- Motor Problem

---

# Alarm Recovery

Before returning to production, verify:

- Fault condition removed
- Safety conditions satisfied
- Equipment ready
- Communication restored
- Operator reset completed
- State machine returned to Ready
